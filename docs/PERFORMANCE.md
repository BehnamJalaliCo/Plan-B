# Performance

Plan-B targets smooth 60/90/120 Hz scrolling and fast start-up on mid-range phones, with data
sets far larger than a typical user's.

## Measured on the JVM (every CI run)

`core/data/src/test/.../LargeDataTest.kt` generates a heavy-user dataset — **5,000 tasks**
(with dates spread over a year, priorities and times), **1,000 notes** of 12 blocks each in 10
notebooks, and **2,000 events** — through the real repositories (so the search index is built
exactly as in the app) and times the hot read paths after a warm-up:

| Query | Result | Time (Robolectric, CI-class machine) | Bound enforced |
|---|---|---|---|
| Today's tasks | Today view of 5,000 tasks | ~50 ms | < 1 s |
| All tasks | 5,000 rows with tag/subtask counts | ~70 ms | < 3 s |
| Month of events | Occurrences for one month | ~2 ms | < 1 s |
| Recent notes | 6 most recent of 1,000 | ~1 ms | < 0.5 s |
| Search (Persian word) | FTS over all entities | ~14 ms | < 1 s |
| Search (prefix) | FTS prefix query | ~12 ms | < 1 s |

The bounds are deliberately loose so they only fail on algorithmic regressions (full scans,
N+1 queries), not on slow CI machines. Backup round-trips of large databases are covered in
`core/backup` tests.

## Design choices

- **Indexed queries.** Foreign keys, due dates, completion state and ordering columns are
  indexed; task lists are a single query with subtask and tag counts computed in SQL.
- **Full-text search** uses an FTS4 table with pre-normalized tokens instead of `LIKE` scans.
- **Recurrence** is expanded lazily and bounded to the requested range; Jalali month boundaries
  are cached per year.
- **Lazy lists** with stable keys (and content types on mixed lists) so Compose reuses item
  compositions; derived values are remembered; state reads are deferred where possible.
- **Off-main-thread work.** Room, DataStore, file I/O and backup run on IO/Default dispatchers.
- **No polling.** "Today" changes come from a minute-aligned ticker; focus progress is computed
  from timestamps.
- **Startup.** The splash screen is held only until settings are read. Notification channels
  and alarm rescheduling run on a background scope.
- **R8** removes unused code and resources: the release APK is about 3 MB (AAB about 7 MB).

## Baseline profile

The release build packages a baseline profile (`assets/dexopt/baseline.prof`) so app code used
at start-up and on the main tabs is precompiled at install time. It is built from:

- `app/src/main/baseline-prof.txt` — a curated profile covering app start-up, navigation, the
  design system, shared UI, data/database read paths and the four main tabs;
- library profiles shipped with Compose, Room, Navigation and other AndroidX artifacts;
- optionally a measured profile generated by `:baselineprofile`
  (`./gradlew :app:generateBaselineProfile`, written to
  `app/src/release/generated/baselineProfiles`).

`profileinstaller` installs the profile on devices where the store does not.

## Macrobenchmarks

`:benchmark` contains:

- `StartupBenchmark` — cold start with `CompilationMode.None` and with the baseline profile;
- `NavigationBenchmark` — frame timing while switching tabs, scrolling lists and opening quick
  capture.

Run on a Gradle-managed Pixel 6 API 34 emulator (hardware virtualization required):

```bash
./gradlew :benchmark:pixel6Api34BenchmarkReleaseAndroidTest
```

Results are written to `benchmark/build/outputs/`. These benchmarks were not run in the
development container (it has no hardware virtualization), so no device numbers are claimed
here; run them on a device or KVM-enabled runner to obtain them.
